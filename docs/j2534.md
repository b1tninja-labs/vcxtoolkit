# Hosting the VCX-NANO as an SAE J2534 pass-through DLL

This is the design for `vcxtoolkit-j2534`: our own SAE J2534-1 pass-through DLL
that exposes the native VCX-NANO through the standard `PassThru*` API, so a
stock J2534 diagnostic application (Techline Connect, GDS2) can drive the dongle
**without** the proprietary VXDIAG / VX-Manager software. `docs/tool-boundary.md`
already reserved this work for this crate: *"A `PassThruSupport.04.04` record, if
one is ever written, belongs here."* This document is that record's design, and
the thin DLL that would carry it.

The DLL **natively drives the dongle.** On Windows `PassThruOpen` opens the
VCX-NANO's serial port, and the exports drive the recovered sequence through the
reusable `vcxtoolkit::Channel` primitives (one copy in the library, shared with any
consumer): `PassThruConnect` runs `Channel::connect_with` (`VCX_PRO_Open(0x8001)` →
`SetComParam` → `SetFilter` → `Start`), `PassThruStartMsgFilter` installs the
flow-control `AddFilter` (`add_flow_control_filter_with`), `PassThruWriteMsgs` sends
through `VCX_PRO_Send` (`send_raw_with`), and `PassThruReadMsgs` reads the pushed
reply frame (`read_msg_with`) and parses the recovered Recv envelope.

The bring-up is hardware-validated. A sibling RE/hardware session read the real
`VCXPT32.dll` and ran the sequence against a VCX-NANO (fw 1.9.4.2): the dongle
accepts the ISO 15765 `VCX_PRO_Open` → `SetComParam` → `SetFilter` → `Start` plus
the flow-control `AddFilter`, the open reply echoes `0x40`, and each send returns a
status ack (`0x9B`) with a TxDone loopback. The library primitives are fake-serial
tested; the live COM4 drive is an `#[ignore]`d owner-run test that sends no vehicle
request.

The read model is **confirmed**, not guessed. A static read of `VCXPT32.dll`
(disassembled directly) shows `PassThruReadMsgs` issues no transmit — it dequeues
from an in-memory queue that an arrival-driven event callback fills: the dongle
*pushes* the ECU reply as its own serial frame, the callback reads it
(`VCX_PRO_Recv`) and enqueues it. So there is **no `VCX_PRO_Recv` request frame** at
the application layer; `read_msg_with` reads the pushed frame and sends nothing. (The
`VCX_PRO_Recv` export's own body stays VMProtect-virtualised in VCX.dll, but it is
invoked only from the arrival callback, never a host poll.) The one real read-path
refinement left is skipping the TxDone / FirstFrame indications J2534 §7.2.3 returns
as messages. Nothing here unlocks the held `collect` read, which is a *separate* gap
(us authoring a `$1A` request, not forwarding the app's).

## Boundary, first

A pass-through DLL is the inverse of this crate's held `collect` path, and the
difference matters for the read-first ethos:

- `collect` would have **us** author a vehicle request (service `$1A`, the
  identifiers, the module CAN id). That content is not recovered from the VXDIAG
  binaries, so `collect` is held (`docs/reads.md`, "The open row").
- A J2534 pass-through authors **no** vehicle request. The diagnostic
  application supplies every request byte in `PASSTHRU_MSG.Data`; the DLL only
  forwards them to the dongle and returns what comes back. The vehicle content is
  the app's, by definition of the standard. So hosting the API synthesizes no new
  vehicle bytes and does not depend on recovering the `$1A` content.

What the DLL still must not do, and does not: write a GM wrapper key
(`HKLM\SOFTWARE\GM\J2534Wrapper` is `spskit`'s, `docs/tool-boundary.md`), build a
programming-data body, or transmit on its own initiative. It writes exactly the
`PassThruSupport.04.04` discovery record and forwards app-supplied frames.

## Where it lives, and how `unsafe` stays caged

A J2534 DLL is a C-ABI `cdylib` whose `extern "system" PassThru*` exports must
cross the C boundary — pointers in, pointers out — which is `unsafe`. The
`vcxtoolkit` library sets `unsafe_code = "forbid"` (`Cargo.toml`), and that is not
relaxed. So the DLL cannot live in the library crate.

It is its own workspace member, `j2534/` (package `vcxtoolkit-j2534`), mirroring
exactly how `winport/` already isolates the Win32 FFI:

```
vcxtoolkit/                 # unsafe_code = "forbid"  (unchanged)
├── Cargo.toml              # now a [workspace] root; winport excluded, j2534 a member
├── winport/                # unsafe_code = "deny"    (Win32 serial/HTTP FFI; untouched)
└── j2534/                  # unsafe_code = "deny"    (the J2534 DLL)
    └── src/
        ├── lib.rs          # module decls; the crate doc
        ├── status.rs       # J2534 return codes + protocol ids (safe)
        ├── msg.rs          # PASSTHRU_MSG (repr C) + a safe owned Msg
        ├── rawmode.rs      # the 4-byte CAN-id raw-mode codec (safe)
        ├── registry.rs     # the PassThruSupport.04.04 record (data; never written)
        ├── engine.rs       # the J2534 → VCX mapping, as pure reference codecs (safe)
        ├── runtime.rs      # the Windows device/channel session; drives vcxtoolkit::Channel (safe)
        └── ffi.rs          # the extern "system" PassThru* exports — the ONLY unsafe
```

The isolation is the same lint idiom `winport` uses: the crate sets
`unsafe_code = "deny"`, and only `ffi.rs` carries `#![allow(unsafe_code)]`. Every
`unsafe` site is therefore one explicit, auditable module; the other five modules
are safe Rust that the gates type-check and unit-test, and all real decisions
delegate to the `vcxtoolkit` codecs (`open_code`, `copied_data`, `send_payload`,
`collect::reply_application_bytes`, `pci::*`).

### The gates still run in one pass

`AGENTS.md` fixes the four gates (`cargo fmt --check`, `cargo clippy --all-targets
-- -D warnings`, `cargo test`, `cargo doc --no-deps`), run from the `vcxtoolkit`
directory with no `--workspace` flag. The root `[workspace]` sets
`default-members = [".", "j2534"]`, so that single pass now covers the library and
the DLL alike. `winport` is kept in `exclude`, not `members`: it stays a path
dependency exactly as before, so the gates neither reformat nor re-lint a file
this change never touched. (Pulling `winport` into the workspace fmt pass surfaced
a pre-existing rustfmt diff in `winport/src/http.rs`; excluding it leaves that
file alone.)

## The exports

J2534-1 specifies `__stdcall` (which Rust spells `extern "system"`: `__stdcall`
on 32-bit x86, the C ABI on x86_64) and a `long` return that is one of the status
codes below. The twelve exports in scope:

| Export | Signature (C) | Behaviour (`j2534/src/ffi.rs` → `runtime` → `vcxtoolkit::Channel`) |
|---|---|---|
| `PassThruOpen` | `long(const void* pName, unsigned long* pDeviceID)` | Opens the VCX-NANO serial port (default COM4); returns a device id. |
| `PassThruClose` | `long(unsigned long DeviceID)` | Drops the session (closes the port). |
| `PassThruConnect` | `long(unsigned long DeviceID, unsigned long ProtocolID, unsigned long Flags, unsigned long BaudRate, unsigned long* pChannelID)` | Runs the ISO 15765 bring-up (`Channel::connect_with`); other protocols → `ERR_NOT_SUPPORTED`; returns the channel id. |
| `PassThruDisconnect` | `long(unsigned long ChannelID)` | Validates the channel id (teardown is on Close). |
| `PassThruReadMsgs` | `long(unsigned long ChannelID, PASSTHRU_MSG* pMsg, unsigned long* pNumMsgs, unsigned long Timeout)` | Reads one pushed reply frame (`Channel::read_msg_with`), parses the Recv envelope into `Data`; `ERR_BUFFER_EMPTY` if none. |
| `PassThruWriteMsgs` | `long(unsigned long ChannelID, const PASSTHRU_MSG* pMsg, unsigned long* pNumMsgs, unsigned long Timeout)` | Frames the app's `Data` and sends it via `VCX_PRO_Send` (`Channel::send_raw_with`). |
| `PassThruStartMsgFilter` | `long(unsigned long ChannelID, unsigned long FilterType, const PASSTHRU_MSG* pMaskMsg, const PASSTHRU_MSG* pPatternMsg, const PASSTHRU_MSG* pFlowControlMsg, unsigned long* pFilterID)` | Installs the flow-control `AddFilter` from the mask/pattern/flow CAN ids (`Channel::add_flow_control_filter_with`); returns the filter id. |
| `PassThruStopMsgFilter` | `long(unsigned long ChannelID, unsigned long FilterID)` | Validates the channel (filters clear on close). |
| `PassThruIoctl` | `long(unsigned long ChannelID, unsigned long IoctlID, void* pInput, void* pOutput)` | Pending (`ERR_NOT_SUPPORTED`); `Connect` already pushes the CAN baud, so `SET_CONFIG` is a follow-up. |
| `PassThruSetProgrammingVoltage` | `long(unsigned long DeviceID, unsigned long PinNumber, unsigned long Voltage)` | Pending (maps to `VCX_DEV_SetPinVol`, not yet wired). |
| `PassThruReadVersion` | `long(unsigned long DeviceID, char* pFirmwareVersion, char* pDllVersion, char* pApiVersion)` | Fills DLL (`vcxtoolkit-j2534 <ver>`) and API (`04.04`); firmware needs a `GetInfo`. |
| `PassThruGetLastError` | `long(char* pErrorDescription)` | Points the caller at the returned status code. |

The remaining three of the classic fifteen — `PassThruStartPeriodicMsg`,
`PassThruStopPeriodicMsg`, and the pair's `ClearPeriodicMsgs`/`ClearMsgFilters`
ioctls — are not wired yet; `vcxtoolkit::forward::periodic_timer`, `add_timer`,
and `stop_timer` already build their payloads, so they are a follow-up, not a gap
in the mapping.

### `PASSTHRU_MSG`

```c
typedef struct {
    unsigned long ProtocolID;
    unsigned long RxStatus;
    unsigned long TxFlags;
    unsigned long Timestamp;
    unsigned long DataSize;
    unsigned long ExtraDataIndex;
    unsigned char Data[4128];
} PASSTHRU_MSG;
```

`msg.rs` mirrors this as `#[repr(C)] PassThruMsg`, and `Msg` is the safe owned
form (the header fields plus `Data[..DataSize]`). The `4128`-byte `Data` cap is
`0x1020` — **the same cap** `vcxtoolkit::MAX_FORWARD` found in the dongle's own
copy routine (`FUN_10005df0`), so a message J2534 accepts fits the `VCX_PRO_Send`
PDU. A `const` assertion pins the two equal.

### Status codes

`status.rs` names the J2534 `long` values the exports return, which are
SAE J2534-2002 §9.2.2.1 Figure 47: `STATUS_NOERROR` (0x00), `ERR_NOT_SUPPORTED`
(0x01), `ERR_INVALID_CHANNEL_ID` (0x02), `ERR_INVALID_PROTOCOL_ID` (0x03),
`ERR_NULL_PARAMETER` (0x04), `ERR_FAILED` (0x07), `ERR_DEVICE_NOT_CONNECTED`
(0x08), `ERR_TIMEOUT` (0x09), `ERR_INVALID_MSG` (0x0A), `ERR_INVALID_IOCTL_ID`
(0x0F). `ERR_INVALID_DEVICE_ID` (0x1A) is a later (04.04) code beyond the 2002
Figure 47 (which ends at 0x15); it is kept because the DLL advertises API `04.04`.
`ERR_BUFFER_EMPTY` (0x10) is what `PassThruReadMsgs` returns when no reply frame has
arrived, and `ERR_NOT_SUPPORTED` is the honest answer for the calls not yet wired
(the ioctls, `SetProgrammingVoltage`) and for a non-ISO 15765 `PassThruConnect`.

### Protocol ids

The only GM channel this host opens is `ISO15765` (id 6); `CAN` (id 5) and the
J1850/ISO9141/ISO14230 ids are named because `vcxtoolkit::open_code` resolves them
to a `VCX_PRO_Open` dword. A unit test asserts every accepted protocol id has such
a dword, so `PassThruConnect` never advertises a channel the dongle has no code
for. ISO 15765 opens as `0x8001`.

## The `PassThruSupport.04.04` registry record

A J2534 application finds this DLL by enumerating
`HKLM\SOFTWARE\PassThruSupport.04.04\<vendor>` (and the `WOW6432Node` twin a
32-bit app reads on 64-bit Windows) and loading the DLL named by
`FunctionLibrary`. `registry.rs` builds the record as pure data:

| Key | `HKLM\SOFTWARE\PassThruSupport.04.04\VXDIAG VCX-NANO - J2534` (+ `WOW6432Node` twin) |
|---|---|
| `Name` | `VXDIAG VCX-NANO - J2534` |
| `Vendor` | `VXDIAG (community vcxtoolkit host)` |
| `FunctionLibrary` | absolute path to the built `vcxtoolkit_j2534.dll` |
| `ProtocolsSupported` | `CAN:ISO15765 (ids 5,6)` |
| `CAN` | `1` |
| `ISO15765` | `1` |
| `APIVersion` | `04.04` |

The `- J2534` key tail matches the shape a real PASSTHRU installer writes
(`docs/tool-boundary.md` notes an installer that writes `<product> - J2534`, and
a second `Bosch - MDI` tail for the same DLL).

**No code path in this crate writes the registry.** `RegistryWrites::register` /
`unregister` build the install/uninstall *plan* and stop there, the same
"build the plan, refuse to act" stance `collect` takes for a vehicle read. The
real `RegCreateKeyEx` / `RegSetValueEx` is an owner-run, Windows-only install step
(`RegistryWrites::OWNER_RUN_NOTE`); the tests never touch `HKLM`.

## Mapping each call onto the recovered VCX protocol

This is the heart of the design, and it is already recovered — the dwords and the
connect sequence were read statically from `VCXPT32.dll` (the registered J2534
pass-through), the caller that *builds* the buffers `VCX.dll` only copies. The
mapping reuses the existing `vcxtoolkit` codecs and synthesizes nothing.

### `PassThruConnect` → open + configure + start

`PassThruConnect` (SAE J2534-2002 §7.2.1, prototype §7.2.1.1) establishes a
protocol channel. `VCXPT32!PassThruConnect` (`FUN_100035e0` → worker
`FUN_10006dc0`) does, in order:

1. `VCX_PRO_Open(openDword)` — `vcxtoolkit::open_code(protocol)`; ISO 15765 = `0x8001`.
2. `VCX_PRO_SetComParam` with one record `{key=3, value=BaudRate}` — `vcxtoolkit::baud_record` + `set_com_param`. The `BaudRate` is the J2534 `DATA_RATE` (§7.3.2, range 5–500000); HS-GMLAN is 500000.
3. `VCX_PRO_SetFilter(1)` — `vcxtoolkit::set_filter_payload(FILTER_PASS)`.
4. `VCX_PRO_Start(0)` — `vcxtoolkit::start_payload`.

`vcxtoolkit::Channel::connect_with` runs exactly this sequence over the serial
seam (fake-serial tested; the `#[ignore]`d hardware test opens the real channel).
The DLL's `runtime::connect` runs it against the open port (only ISO 15765 is wired
natively; other protocols return `ERR_NOT_SUPPORTED`), and `PassThruConnect`
returns the channel id. The bring-up is hardware-accepted by the dongle, and it
configures the channel without transmitting to a vehicle. This missing bring-up was
the diagnosis behind a sibling session's constant-`0x9E`/`0x9B` read: without
`SetComParam`/`Start` the channel never runs, so the dongle answers with its
un-configured status instead of the ECU's.

### `PassThruStartMsgFilter` → the flow-control `AddFilter`

`PassThruStartMsgFilter` with `FilterType = FLOW_CONTROL_FILTER` (0x03;
SAE J2534-2002 §7.2.1.1 Figure 11) takes three `PASSTHRU_MSG`s — a `MaskMsg`, a
`PatternMsg`, and a `FlowControlMsg` (§9.2.2.1). For ISO 15765 the mask is
`FF FF FF FF`, the pattern the ECU response id, and the flow-control the tester
request id, each the 4-byte CAN id at the front of the message data (§8.3.2).
`VCXPT32` forwards it as `VCX_PRO_AddFilter`. `runtime::add_flow_filter` pulls the
response and request ids out of the pattern and flow-control messages and installs
the native record via `Channel::add_flow_control_filter_with` (built by
`vcxtoolkit::flow_control_filter`, a kind-3 filter that carries the flow-control
bytes); `PassThruStartMsgFilter` returns the filter id. Without the filter the
dongle never delivers the reply.

### `PassThruWriteMsgs` → `VCX_PRO_Send`, and the raw-mode CAN id

`PassThruWriteMsgs` (SAE J2534-2002 §7.2.1 lists it as §7.2.4) transmits the app's
messages. `ConvertPassthruMsg` (`FUN_10005df0`) copies `PASSTHRU_MSG.Data` to the
Send PDU's offset 6 **verbatim** (only TP2.0 strips a leading 4), and
`VCX_PRO_Send` frames it. That is exactly `vcxtoolkit::copied_data` +
`send_payload`, which `Channel::send_raw_with` builds and writes to the port;
`runtime::write` drives it. The returned frame is the device status ack (`0x9B`),
not the ECU reply — which arrives separately and is read by `PassThruReadMsgs`.
(`engine::write_send_pdu` is the same construction as a pure reference codec.)

The one correctness subtlety is the **CAN id prefix**. In raw / PassThru mode a
J2534 ISO 15765 `Data` field is `[4-byte CAN id, big-endian][service][payload…]`.
SAE J2534-2002 is directly normative:

> "Offset 0 … CANID bits 24-29 … Offset 3 CANID bits 0-7 … Offset 4 First data
> byte of message"
> — SAE J2534 (2002) §8.3.2 "ISO 15765-4 DATA FORMAT", Figure 36
> (confirmed in `primarysource`, `sae:j2534-2002`). §8.3.2.1 makes a `DataSize`
> under four bytes an `ERR_INVALID_MSG`.

So a `$1A C1` read to `0x7E0` rides the wire as `00 00 07 E0 1A C1`. `rawmode.rs`
is the pure codec for this split (`split`/`join`), with the 4-byte id and the
application bytes named but neither invented — the app owns both. `write_send_pdu`
confirms an ISO 15765 message carries its id (else `ERR_INVALID_MSG`), then hands
the whole data field to the dongle, which adds the ISO-TP single-frame PCI itself.
The `TxFlags` the app may set — `CAN_29BIT_ID` (bit 8), `ISO15765_ADDR_TYPE`
(bit 7), `ISO15765_FRAME_PAD` (bit 6) — are SAE J2534-2002 §8.4 Figure 43, which
`vcxtoolkit::pdu_flags` maps.

### `PassThruReadMsgs` → the pushed reply frame

`PassThruReadMsgs` (SAE J2534-2002 §7.2.1 lists it as §7.2.3) reads queued
messages. The reply envelope *layout* is recovered from the non-virtualized
`VCXPT32!ConvertVCXMsg` (`FUN_10006070`): a little-endian flag word at offset 0, a
little-endian length at offset 4, then the data at offset 6, with every ISO 15765
byte kept. That is `vcxtoolkit::collect::reply_application_bytes`, which the DLL
applies to the frame `Channel::read_msg_with` returns, and the reply `Data` keeps
its leading 4-byte rx id (`00 00 07 E8 5A C1 …`), symmetric to the write side
(§8.3.2).

The **fetch mechanism is confirmed**: a direct disassembly of `VCXPT32.dll` shows
`PassThruReadMsgs` issues no transmit — it dequeues from an in-memory queue an
arrival-driven event callback fills. The dongle *pushes* the ECU reply as its own
serial frame; the callback reads it (`VCX_PRO_Recv`, `[0x10013cd0]`) and enqueues
it, while `VCX_PRO_Send` on the write path returns only a status ack (`0x9B`). So
there is **no `VCX_PRO_Recv` request frame** at the application layer (the inferred
`0x44` does not exist), and `Channel::read_msg_with` / `exchange::read_message`
read the pushed frame without writing — which is what the DLL does. The one
remaining read-path item is skipping the TxDone / FirstFrame indications §7.2.3
requires surfaced as messages (filter by `RxStatus`); `PassThruReadMsgs` returns
`ERR_BUFFER_EMPTY` when no frame has arrived.

### `PassThruIoctl`, `PassThruSetProgrammingVoltage`

`PassThruIoctl(SET_CONFIG)` (SAE J2534-2002 §7.2.1 lists it as §7.2.12; the ioctl
§7.3.2) carries an `SCONFIG_LIST` of `(Parameter, Value)` pairs whose `DATA_RATE`
(0x01) maps to the native `SetComParam` baud record (`vcxtoolkit::baud_record`,
key 3). The DLL's `PassThruConnect` already pushes that baud through
`Channel::connect_with`, so a separate `SET_CONFIG` is a follow-up and
`PassThruIoctl` returns `ERR_NOT_SUPPORTED` today rather than a partial mapping.
`SetProgrammingVoltage` maps to `VCX_DEV_SetPinVol` (`vcxtoolkit::set_pin_vol`) and
is likewise pending; its payload builder already exists.

### A note on `vcikit`

A sibling plan, `vcikit`, models the *internal* raw-mode seam (the 4-byte id,
the ComParam set, the connect→configure→start→send/recv→stop lifecycle) as a
transport-agnostic `Backend` trait between a driver (`gmdiag`) and a dongle. This
J2534 DLL is the **outward** face of the same lifecycle: it *hosts* the standard
API for third-party apps rather than consuming one. The two are complementary —
the raw-mode CAN-id convention in `rawmode.rs` here is the same convention
`vcikit` would centralize — and share no code today.

## The SAE J2534 clause map

SAE J2534 (2002) **is** now citable from `primarysource` (`sae:j2534-2002`, the
`sae_*` tools), so this host is grounded directly in the standard rather than the
earlier ISO 22900-2 stand-in. Each mapped call and the clause it rests on:

| J2534 call / value | SAE J2534-2002 clause |
|---|---|
| `PassThruConnect`, the API function list | §7.2.1 (names §7.2.3 ReadMsgs, §7.2.4 WriteMsgs, §7.2.7 StartMsgFilter, §7.2.12 Ioctl) |
| C/C++ prototypes; `FilterType` values (`FLOW_CONTROL_FILTER = 0x03`, Figure 11) | §7.2.1.1 |
| `PassThruIoctl(SET_CONFIG)`: `SCONFIG_LIST`/`SCONFIG`, `DATA_RATE = 0x01` (5–500000) | §7.3.2 |
| ISO 15765-4 data format: 4-byte CAN id prefix (Figure 36); `DataSize < 4` → `ERR_INVALID_MSG` | §8.3.2 / §8.3.2.1 |
| `TxFlags`: `CAN_29BIT_ID` (8), `ISO15765_ADDR_TYPE` (7), `ISO15765_FRAME_PAD` (6), Figure 43 | §8.4 |
| `PassThruSupport.04.04` registry (`Name`, `ProtocolsSupported`, `FunctionLibrary`) | §9.2.1 |
| Export ordinals (`@1`–`@12`); return-code values (Figure 47) | §9.2.2.1 |

The raw-mode 4-byte CAN-id convention is corroborated by ISO 22900-2:2009
§9.2.6.3.6 (also in `primarysource`), but §8.3.2 above is the direct SAE source.
Per the workspace rule, every clause here was confirmed with the `sae_*` tools,
never paraphrased from memory.

The DLL drives the dongle with recovered, hardware-accepted codecs — it opens the
port, runs the bring-up, sends the app's bytes, and reads the pushed reply — but it
synthesizes no vehicle request (the app owns `Data`), never writes the registry,
and never flips `collect::READ_LAYOUT_RECOVERED`. End-to-end proof against a live
vehicle (an awake ECU reply) is owner-run through a real J2534 app, not an auto-run
test. Every wire decision is a recovered
`vcxtoolkit` codec rather than an invented frame.
