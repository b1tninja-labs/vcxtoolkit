# Hosting the VCX-NANO as an SAE J2534 pass-through DLL

This is the design for `vcxtoolkit-j2534`: our own SAE J2534-1 pass-through DLL
that exposes the native VCX-NANO through the standard `PassThru*` API, so a
stock J2534 diagnostic application (Techline Connect, GDS2) can drive the dongle
**without** the proprietary VXDIAG / VX-Manager software. `docs/tool-boundary.md`
already reserved this work for this crate: *"A `PassThruSupport.04.04` record, if
one is ever written, belongs here."* This document is that record's design, and
the thin DLL that would carry it.

It is design-forward. The native VCX vehicle exchange is still unproven on
hardware (a bench `TesterPresent` returns a dongle status byte, no vehicle —
`ROADMAP.md`), so nothing here claims a working vehicle path, and the DLL does
not unlock the held `collect` read. What ships today is a **scaffold**: the
export signatures, the `PASSTHRU_MSG` layout, the raw-mode convention, the
J2534→VCX mapping, and the registry record, all built and tested, with the
channel-bearing calls returning `ERR_NOT_SUPPORTED` (pending) rather than
pretending a link exists.

## Boundary, first

A pass-through DLL is the inverse of this crate's held `collect` path, and the
difference matters for the read-first ethos:

- `collect` would have **us** author a vehicle request (service `$1A`, the
  identifiers, the module CAN id). That content is not recovered from the VXDIAG
  binaries, so `collect` is held (`docs/reads.md`, "The open row").
- A J2534 pass-through authors **no** vehicle request. The diagnostic
  application supplies every request byte in `PASSTHRU_MSG.Data`; the DLL only
  forwards them to the dongle and returns what comes back. The vehicle content is
  the app's, by definition of the standard. So hosting the API synthesizes no new
  vehicle bytes and does not depend on recovering the `$1A` content.

What the DLL still must not do, and does not: write a GM wrapper key
(`HKLM\SOFTWARE\GM\J2534Wrapper` is `spskit`'s, `docs/tool-boundary.md`), build a
programming-data body, or transmit on its own initiative. It writes exactly the
`PassThruSupport.04.04` discovery record and forwards app-supplied frames.

## Where it lives, and how `unsafe` stays caged

A J2534 DLL is a C-ABI `cdylib` whose `extern "system" PassThru*` exports must
cross the C boundary — pointers in, pointers out — which is `unsafe`. The
`vcxtoolkit` library sets `unsafe_code = "forbid"` (`Cargo.toml`), and that is not
relaxed. So the DLL cannot live in the library crate.

It is its own workspace member, `j2534/` (package `vcxtoolkit-j2534`), mirroring
exactly how `winport/` already isolates the Win32 FFI:

```
vcxtoolkit/                 # unsafe_code = "forbid"  (unchanged)
├── Cargo.toml              # now a [workspace] root; winport excluded, j2534 a member
├── winport/                # unsafe_code = "deny"    (Win32 serial/HTTP FFI; untouched)
└── j2534/                  # unsafe_code = "deny"    (the J2534 DLL)
    └── src/
        ├── lib.rs          # module decls; the crate doc
        ├── status.rs       # J2534 return codes + protocol ids (safe)
        ├── msg.rs          # PASSTHRU_MSG (repr C) + a safe owned Msg
        ├── rawmode.rs      # the 4-byte CAN-id raw-mode codec (safe)
        ├── registry.rs     # the PassThruSupport.04.04 record (data; never written)
        ├── engine.rs       # the J2534 → VCX mapping (safe; delegates to vcxtoolkit)
        └── ffi.rs          # the extern "system" PassThru* exports — the ONLY unsafe
```

The isolation is the same lint idiom `winport` uses: the crate sets
`unsafe_code = "deny"`, and only `ffi.rs` carries `#![allow(unsafe_code)]`. Every
`unsafe` site is therefore one explicit, auditable module; the other five modules
are safe Rust that the gates type-check and unit-test, and all real decisions
delegate to the `vcxtoolkit` codecs (`open_code`, `copied_data`, `send_payload`,
`collect::reply_application_bytes`, `pci::*`).

### The gates still run in one pass

`AGENTS.md` fixes the four gates (`cargo fmt --check`, `cargo clippy --all-targets
-- -D warnings`, `cargo test`, `cargo doc --no-deps`), run from the `vcxtoolkit`
directory with no `--workspace` flag. The root `[workspace]` sets
`default-members = [".", "j2534"]`, so that single pass now covers the library and
the DLL alike. `winport` is kept in `exclude`, not `members`: it stays a path
dependency exactly as before, so the gates neither reformat nor re-lint a file
this change never touched. (Pulling `winport` into the workspace fmt pass surfaced
a pre-existing rustfmt diff in `winport/src/http.rs`; excluding it leaves that
file alone.)

## The exports

J2534-1 specifies `__stdcall` (which Rust spells `extern "system"`: `__stdcall`
on 32-bit x86, the C ABI on x86_64) and a `long` return that is one of the status
codes below. The twelve exports in scope:

| Export | Signature (C) | Scaffold behaviour |
|---|---|---|
| `PassThruOpen` | `long(const void* pName, unsigned long* pDeviceID)` | Returns a device id; no hardware needed. |
| `PassThruClose` | `long(unsigned long DeviceID)` | Validates the id; `NOERROR`. |
| `PassThruConnect` | `long(unsigned long DeviceID, unsigned long ProtocolID, unsigned long Flags, unsigned long BaudRate, unsigned long* pChannelID)` | Validates the protocol via `engine::connect_open_code`, then **pending**. |
| `PassThruDisconnect` | `long(unsigned long ChannelID)` | No live channel → `ERR_INVALID_CHANNEL_ID`. |
| `PassThruReadMsgs` | `long(unsigned long ChannelID, PASSTHRU_MSG* pMsg, unsigned long* pNumMsgs, unsigned long Timeout)` | Reports 0 read, then **pending**. |
| `PassThruWriteMsgs` | `long(unsigned long ChannelID, const PASSTHRU_MSG* pMsg, unsigned long* pNumMsgs, unsigned long Timeout)` | Reports 0 sent, then **pending**. |
| `PassThruStartMsgFilter` | `long(unsigned long ChannelID, unsigned long FilterType, const PASSTHRU_MSG* pMaskMsg, const PASSTHRU_MSG* pPatternMsg, const PASSTHRU_MSG* pFlowControlMsg, unsigned long* pFilterID)` | No live channel → `ERR_INVALID_CHANNEL_ID`. |
| `PassThruStopMsgFilter` | `long(unsigned long ChannelID, unsigned long FilterID)` | `ERR_INVALID_CHANNEL_ID`. |
| `PassThruIoctl` | `long(unsigned long ChannelID, unsigned long IoctlID, void* pInput, void* pOutput)` | **pending**. |
| `PassThruSetProgrammingVoltage` | `long(unsigned long DeviceID, unsigned long PinNumber, unsigned long Voltage)` | Validates the device; **pending** (maps to `VCX_DEV_SetPinVol`). |
| `PassThruReadVersion` | `long(unsigned long DeviceID, char* pFirmwareVersion, char* pDllVersion, char* pApiVersion)` | Fills DLL (`vcxtoolkit-j2534 <ver>`) and API (`04.04`); firmware pending. |
| `PassThruGetLastError` | `long(char* pErrorDescription)` | Writes the pending-hardware description. |

The remaining three of the classic fifteen — `PassThruStartPeriodicMsg`,
`PassThruStopPeriodicMsg`, and the pair's `ClearPeriodicMsgs`/`ClearMsgFilters`
ioctls — are not in this scaffold; `vcxtoolkit::forward::periodic_timer`,
`add_timer`, and `stop_timer` already build their payloads, so they are a
follow-up, not a gap in the mapping.

### `PASSTHRU_MSG`

```c
typedef struct {
    unsigned long ProtocolID;
    unsigned long RxStatus;
    unsigned long TxFlags;
    unsigned long Timestamp;
    unsigned long DataSize;
    unsigned long ExtraDataIndex;
    unsigned char Data[4128];
} PASSTHRU_MSG;
```

`msg.rs` mirrors this as `#[repr(C)] PassThruMsg`, and `Msg` is the safe owned
form (the header fields plus `Data[..DataSize]`). The `4128`-byte `Data` cap is
`0x1020` — **the same cap** `vcxtoolkit::MAX_FORWARD` found in the dongle's own
copy routine (`FUN_10005df0`), so a message J2534 accepts fits the `VCX_PRO_Send`
PDU. A `const` assertion pins the two equal.

### Status codes

`status.rs` names the J2534-1 `long` values the exports return:
`STATUS_NOERROR` (0x00), `ERR_NOT_SUPPORTED` (0x01), `ERR_INVALID_CHANNEL_ID`
(0x02), `ERR_INVALID_PROTOCOL_ID` (0x03), `ERR_NULL_PARAMETER` (0x04),
`ERR_FAILED` (0x07), `ERR_DEVICE_NOT_CONNECTED` (0x08), `ERR_TIMEOUT` (0x09),
`ERR_INVALID_MSG` (0x0A), `ERR_INVALID_DEVICE_ID` (0x1A). The scaffold uses
`ERR_NOT_SUPPORTED` as the honest "recovered but unproven on hardware" answer.

### Protocol ids

The only GM channel this host opens is `ISO15765` (id 6); `CAN` (id 5) and the
J1850/ISO9141/ISO14230 ids are named because `vcxtoolkit::open_code` resolves them
to a `VCX_PRO_Open` dword. A unit test asserts every accepted protocol id has such
a dword, so `PassThruConnect` never advertises a channel the dongle has no code
for. ISO 15765 opens as `0x8001`.

## The `PassThruSupport.04.04` registry record

A J2534 application finds this DLL by enumerating
`HKLM\SOFTWARE\PassThruSupport.04.04\<vendor>` (and the `WOW6432Node` twin a
32-bit app reads on 64-bit Windows) and loading the DLL named by
`FunctionLibrary`. `registry.rs` builds the record as pure data:

| Key | `HKLM\SOFTWARE\PassThruSupport.04.04\VXDIAG VCX-NANO - J2534` (+ `WOW6432Node` twin) |
|---|---|
| `Name` | `VXDIAG VCX-NANO - J2534` |
| `Vendor` | `VXDIAG (community vcxtoolkit host)` |
| `FunctionLibrary` | absolute path to the built `vcxtoolkit_j2534.dll` |
| `ProtocolsSupported` | `CAN:ISO15765 (ids 5,6)` |
| `CAN` | `1` |
| `ISO15765` | `1` |
| `APIVersion` | `04.04` |

The `- J2534` key tail matches the shape a real PASSTHRU installer writes
(`docs/tool-boundary.md` notes an installer that writes `<product> - J2534`, and
a second `Bosch - MDI` tail for the same DLL).

**No code path in this crate writes the registry.** `RegistryWrites::register` /
`unregister` build the install/uninstall *plan* and stop there, the same
"build the plan, refuse to act" stance `collect` takes for a vehicle read. The
real `RegCreateKeyEx` / `RegSetValueEx` is an owner-run, Windows-only install step
(`RegistryWrites::OWNER_RUN_NOTE`); the tests never touch `HKLM`.

## Mapping each call onto the recovered VCX protocol

This is the heart of the design, and it is already recovered — the dwords and the
connect sequence were read statically from `VCXPT32.dll` (the registered J2534
pass-through), the caller that *builds* the buffers `VCX.dll` only copies. The
mapping reuses the existing `vcxtoolkit` codecs and synthesizes nothing.

### `PassThruConnect` → open + configure + start

`VCXPT32!PassThruConnect` (`FUN_100035e0` → worker `FUN_10006dc0`) does, in order:

1. `VCX_PRO_Open(openDword)` — `vcxtoolkit::open_code(protocol)`; ISO 15765 = `0x8001`.
2. `VCX_PRO_SetComParam` with one record `{key=3, value=BaudRate}` — `vcxtoolkit::forward::baud_record` + `set_com_param`. For HS-GMLAN the baud is 500000.
3. `VCX_PRO_SetFilter(1)` — `vcxtoolkit::forward::set_filter_payload(FILTER_PASS)`.
4. `VCX_PRO_Start(0)` — `vcxtoolkit::forward::start_payload`.

The scaffold's `engine::connect_open_code` performs step 1's lookup and validates
the protocol; steps 2–4 (the channel bring-up) are recovered and buildable from
the already-public `forward` helpers, but opening a *live* channel is the
unproven hardware path, so `PassThruConnect` returns pending after validating.
This missing bring-up is the diagnosis behind a sibling session's constant-`0x9E`
read: without `SetComParam`/`Start` the channel never runs.

### `PassThruStartMsgFilter` → the flow-control `AddFilter`

To receive ISO 15765 replies the app installs a `FLOW_CONTROL` filter whose
mask/pattern/flow are the CAN ids (`FF FF FF FF` / response id / request id);
`VCXPT32` forwards it as `VCX_PRO_AddFilter`. That maps onto
`vcxtoolkit::forward::start_filter` (a kind-3 filter carries the flow-control
bytes). Without it the dongle does not deliver the reply.

### `PassThruWriteMsgs` → `VCX_PRO_Send`, and the raw-mode CAN id

`ConvertPassthruMsg` (`FUN_10005df0`) copies `PASSTHRU_MSG.Data` to the Send PDU's
offset 6 **verbatim** (only TP2.0 strips a leading 4), and `VCX_PRO_Send` frames
it. That is exactly `vcxtoolkit::copied_data` + `send_payload`, which the
scaffold's `engine::write_send_pdu` calls — building the PDU and holding it, never
transmitting.

The one correctness subtlety is the **CAN id prefix**. In raw / PassThru mode a
J2534 ISO 15765 `Data` field is `[4-byte CAN id, big-endian][service][payload…]`,
and this is normative, not a VXDIAG quirk:

> "For ISO 15765, SAE J1939, and ISO 11898, the first 4 bytes of the pCopData
> shall be the CAN ID (11 bit or 29 bit)."
> — ISO 22900-2:2009, §9.2.6.3.6 "ComPrimitives in raw mode (PassThru)"
> (confirmed in `primarysource`, `iso:22900-2@2009`; §11.1.4.18.5 repeats it).

So a `$1A C1` read to `0x7E0` rides the wire as `00 00 07 E0 1A C1`. `rawmode.rs`
is the pure codec for this split (`split`/`join`), with the 4-byte id and the
application bytes named but neither invented — the app owns both. `write_send_pdu`
confirms an ISO 15765 message carries its id, then hands the whole data field to
the dongle, which adds the ISO-TP single-frame PCI itself.

### `PassThruReadMsgs` → `VCX_PRO_Recv` envelope

The virtualized `VCX_PRO_Recv` only fills the PDU; its shape is read by the
non-virtualized `VCXPT32!ConvertVCXMsg` (`FUN_10006070`): a little-endian flag
word at offset 0, a little-endian length at offset 4, then the data at offset 6,
with every ISO 15765 byte kept. That is `vcxtoolkit::collect::reply_application_bytes`,
which `engine::read_application_bytes` applies. The reply `Data` keeps its leading
4-byte rx id (`00 00 07 E8 5A C1 …`) — the app expects it, symmetric to the write
side.

### `PassThruIoctl`, `PassThruSetProgrammingVoltage`

`SetProgrammingVoltage` maps to `VCX_DEV_SetPinVol` (`vcxtoolkit::set_pin_vol`);
`READ_PROG_VOLTAGE` and the config ioctls map to the `SET_CONFIG` records
`vcxtoolkit::forward::config_records` builds. The scaffold validates and returns
pending; the payload builders already exist.

### A note on `vcikit`

A sibling plan, `vcikit`, models the *internal* raw-mode seam (the 4-byte id,
the ComParam set, the connect→configure→start→send/recv→stop lifecycle) as a
transport-agnostic `Backend` trait between a driver (`gmdiag`) and a dongle. This
J2534 DLL is the **outward** face of the same lifecycle: it *hosts* the standard
API for third-party apps rather than consuming one. The two are complementary —
the raw-mode CAN-id convention in `rawmode.rs` here is the same convention
`vcikit` would centralize — and share no code today.

## The SAE J2534 spec gap

SAE J2534 is **not citable from `primarysource`**. The document exists in the SAE
collection (`j2534@2002`) but the `sae_*` tools are not on `main`: the collection
sits on an unmerged branch behind a terms gate that needs the owner's own
`PRIMARYSOURCE_SAE_ACCEPT_TERMS` (confirmed by the primarysource owner session,
2026-11-22). So this design is grounded in **public J2534-1 API knowledge** for
the export signatures, the `PASSTHRU_MSG` layout, and the status/protocol numbers,
and in the **ISO 22900-2:2009 (D-PDU API) stand-in** — present and confirmed in
`primarysource` — wherever a normative clause applies:

- §9.2.6.3.6 — the raw-mode 4-byte CAN-id prefix (above).
- §11.1.4.18.5 — "Expected response structure": the CAN id is in the first four
  bytes of the PDU data; the clause states the ISO 15765 protocol id is identical
  to protocol ID CAN in SAE J2534-1.

When the SAE collection is enabled, swap the ISO stand-in for direct
`sae:j2534@2002` citations and record the clause map. Until then, never paraphrase
either standard from memory — the workspace rule holds, and every clause above was
confirmed with the `iso_*` tools.

## Status, and what is proven

| Piece | State |
|---|---|
| Export signatures, `__stdcall`, `PASSTHRU_MSG`, status/protocol codes | **Built, tested** (`status`, `msg`, `ffi`). |
| Raw-mode 4-byte CAN-id codec | **Built, tested** (`rawmode`), grounded in ISO 22900-2 §9.2.6.3.6. |
| J2534 → VCX mapping (open dword, Send PDU, Recv envelope) | **Built, tested** (`engine`), delegating to `vcxtoolkit`. |
| `PassThruSupport.04.04` record + register/unregister plan | **Built, tested** (`registry`); never writes `HKLM`. |
| Live channel bring-up (`SetComParam`/`SetFilter`/`Start` + flow filter) | **Recovered, not proven on a vehicle.** Channel calls return `ERR_NOT_SUPPORTED` (pending). |
| The `$1A` vehicle request content | **Not ours to author.** The app supplies it; `collect` stays held independently. |
| Real registry write | **Owner-run, Windows-only.** Not implemented; the plan is built and held. |

Nothing here transmits to a vehicle, opens a live channel, writes the registry,
or flips `collect::READ_LAYOUT_RECOVERED`. The DLL is honest scaffolding that a
J2534 app can load and discover, that reports its versions and a clear
pending-hardware error, and whose every wire decision is a recovered `vcxtoolkit`
codec rather than an invented frame.
